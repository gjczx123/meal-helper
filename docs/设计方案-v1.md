# 三餐助手 · 无人值守版设计方案 v1.1

> 状态：待确认（未开始编码）
> 2026-11-01 修订：核心收窄为「提醒 + 记录」，去掉追问、语音、防休眠

## 1. 目标

每天 08:30 / 12:30 / 18:30，自动在微信里提醒她报备三餐；她把吃了什么（文字或照片）发回来，
系统自动读取、记录成台账；能看懂的顺带判一下是否超她自己定的餐标，看不懂就只记原文，不打扰她。
**全程不需要有人看屏幕。**

一句话：**提醒她按时吃饭报备，同时把每顿都记下来。**

### 非目标
- 不做营养建议，只按她给的标准比对
- 不追问、不催、不纠正她的说法（识别不了就安静记录）
- v1 不处理语音消息
- 不读除她以外的任何会话；不做群发

## 2. 一天的运行流程

    08:30  发提醒 ──► 等待窗口 30 分钟（每 15 秒查一次）
              ├─ 收到文字 ──► 存原文 ──► 尽力解析 ──► 判定 ──► 记账 ──► 回一句确认
              ├─ 收到照片 ──► 存图 ──► 视觉识别 ──► 判定 ──► 记账 ──► 回一句确认
              ├─ 收到语音／看不懂 ──► 只存原文，标「未识别」──► 不回（不打扰）
              └─ 30 分钟没回 ──► 记「未报备」──► 结束，不催

    12:30 / 18:30  同上
    周日 20:00  周报（发给你）

## 3. 系统组成

    scheduler ──► service（一顿饭的流程） ──► sender ──► 微信
                      │                        │
                      │                        └──► 读库校验发送是否成功
                      ├──► reader（读她的回复 + 图片路径）
                      ├──► parse / analyze / reply（纯逻辑）
                      └──► db（台账）+ notify（失败通知）

- 纯逻辑（解析、判定、话术、状态机、调度时间计算）全部可单测，不碰系统
- OS 相关的只有三块：窗口/输入（win32）、读库（decrypt + reader）、通知

## 4. 关键决策

### 4.1 发送
微信 4.x 是 Qt/Chromium，后台按键无效，只能在发送瞬间把窗口提上来：

1. 保存当前前台窗口 → SetForegroundWindow(微信) → Ctrl+F 搜备注 → 回车进会话
2. 点输入框 → 剪贴板粘贴 → 回车 → 还原前台窗口（约 1.5–2 秒）
3. **发送后必须读库校验**：这条消息真的出现在她的会话里才算成功
4. 失败重发 1 次；再失败不重试，写日志 + 弹通知

细节：
- 进程启动时设 `PROCESS_PER_MONITOR_DPI_AWARE`，所有坐标统一用物理像素（现在 150% 缩放下
  两套坐标系并存，就是之前截图和点击错位的根源）
- 发送前检查键鼠空闲 ≥ 3 秒；你在打字就每 5 秒重试，最多等 2 分钟
- 不再用 pyautogui / pyperclip / uiautomation，改成 ctypes 直调 Win32（少三个依赖）

### 4.2 接收
已确认的事实：微信 4.2.0.12，数据在 `<你的微信数据目录>/`，
消息库 `db_storage/message/message_0.db` 是 SQLCipher 加密，密钥要在 `Weixin.exe` 内存里取。

读法：复制 `message_0.db` + `-wal` 到临时目录 → 取密钥解密 → 按会话取「提问之后、她发的」消息。
能直接拿到：原文、发送者、时间戳、**图片的本地文件路径**（照片不需要走 OCR）。

兜底：解密失败（多为微信升级）→ 切 `PrintWindow` 截图 + OCR。已实测：窗口被完全遮挡时
`PrintWindow` 仍能拿到完整界面，所以兜底也不要求窗口在前台。

### 4.3 餐标 = 7 天循环菜单（哥本 5+2 轻断食）

标准不再是一堆食物类别，而是**一张 7 天菜单**，7 天一轮循环：

| 天 | 类型 | 早 | 午 | 晚 | kcal |
|---|---|---|---|---|---|
| DAY1 | 正常 | 全麦吐司 + 豆浆粉 | 午餐肉 + 魔芋面 | 黑束带奶昔 | 802 |
| DAY2 | 轻断 | 夹心蛋 + 黑咖啡 | 奇亚籽饼干 + 羽衣甘蓝粉 | 低脂鸡胸肉 + 羽衣甘蓝粉 | 205 |
| DAY3 | 正常 | 全麦吐司 + 黑咖啡 | 夹心蛋 + 魔芋面 | 黑束带奶昔 | 681 |
| DAY4 | 轻断 | 夹心蛋 + 黑咖啡 | 鸡肉火腿片 + 羽衣甘蓝粉 | 笋尖鸡肉肠 + 羽衣甘蓝粉 | 147 |
| DAY5 | 正常 | 奇亚籽饼干 + 豆浆粉 | 午餐肉 + 魔芋面 | 黑束带奶昔 | 760 |
| DAY6 | 正常 | 全麦吐司 + 黑咖啡 | 笋尖鸡肉肠 + 魔芋面 | 黑束带奶昔 | 661 |
| DAY7 | 正常 | 全麦吐司 + 黑咖啡 | 鸡肉火腿片 + 魔芋面 | 黑束带奶昔 | 664 |

- 每项配别名，例如「全麦吐司」接受「全麦面包」「吐司」「面包」；「黑束带奶昔」接受「奶昔」
- `cycle_start` 记录 DAY1 是哪天，默认首次启动日，设置页可改
- 界面里做成表格，她想换餐可以直接改某天某餐的条目

### 4.4 判定（严格模式，按你的口径）

她报的每一样都要对得上**当天该餐的菜单**：

| 情况 | 判定 |
|---|---|
| 名称命中计划项，数量 ≤ 计划量 | 合规 |
| 名称命中，但吃了两份（计划一份） | **超量 → 超标** |
| 名称对不上任何计划项（米饭、奶茶、面条、炸鸡） | **计划外 → 超标** |
| 她说「没吃」「不饿」 | 未进食，不判、不警告 |
| 完全看不懂 | 未识别，不判、不回复 |

结果四态：`normal` / `over`（带原因：计划外 X、超量 Y）/ `fasting`（未进食）/ `unparsed`。

**轻断日特殊处理**：DAY2 / DAY4 本来就是 205 / 147 kcal。她在轻断日说没吃 → 回一句鼓励；
正常日说没吃 → 回「记得吃点东西呀」，仍不警告。

### 4.5 应答（轻，不报数字）
- 合规：「收到，今天这样挺好～」
- 超标：「这个不在计划里哦，晚上注意点～」（只说是什么，不说热量、不说份数）
- 未进食：轻断日「不吃也行，多喝水～」；正常日「记得吃点呀」
- 未识别：不回
### 4.5 台账
重建 meals.db：

    meal_records(id, date, meal, msg_time, source[text|image|voice], raw_text, image_path,
                 plan_day, items_json, status[normal|over|fasting|unparsed|voice|missed],
                 verdict_reason, analysis_json, reply_text, sent_at, verify_ok)
    message_seen(msg_id PRIMARY KEY, ts)     -- 去重，重启不会重复处理/回复

### 4.6 可靠性
- 单实例锁（防止两份进程抢窗口）
- 日志落盘 `logs/app-YYYY-MM-DD.log`
- 任何失败都弹 Windows 通知，不静默
- 开机自启（计划任务）；启动后若当天某餐还在 30 分钟窗口内就补发，过期记 missed
- 电脑不休眠（你确认过不会关机，所以不做防休眠）

### 4.7 锁屏（你白天会锁屏，这条必须处理）

锁屏状态下 Windows 不允许程序操作其他窗口，发送一定失败。处理办法：

1. **首次启动提供一键设置「保持不锁屏」**：关闭屏保、关闭锁屏密码、禁止睡眠（写注册表，可随时撤销）
2. 每次发送前 5 分钟检测会话是否锁定；已锁定 → 记 `missed`，托盘变红并通知你，不硬发
3. 解锁后 30 分钟内自动补发一次；超过就只记 `missed`
4. 如果你坚持用锁屏，首页会明确显示「锁屏期间无法提醒」，不会假装成功
## 5. 失败模式

| 情况 | 处理 |
|---|---|
| 微信没登录 / 找不到窗口 | 不猜、不发，通知你，等下一餐 |
| 发送失败 | 重试 1 次，再失败通知，绝不刷屏 |
| 读库失败（微信升级） | 切截图 OCR 兜底，并通知「读库失效，该维护了」 |
| 她回语音 | 只记录，不回复 |
| 她回「随便吃了点」 | 存原文，标未识别，不回复 |
| 重启后错过 | 窗口内补发，过期记 missed |
| 同一条消息重复处理 | message_seen 去重 |

## 6. 已确认的需求（2026-11-01）

| 问题 | 结论 |
|---|---|
| 她知情吗 | 知道，接受被提醒 |
| 提醒语义 | 既要提醒吃饭，也要催报备 |
| 回复形态 | 以打字为主，图片为辅（识别不求精细，主要看量） |
| 判定口径 | 份量；严格模式：不在计划内就算超，计划内超量也算超 |
| 监督程度 | 轻，但把她当被监督的人 |
| 电脑状态 | 白天会锁屏（优先解决锁屏可执行，做不到就不锁屏） |
| 最不能接受的错误 | 发错人 |
| 数据保留 | 2 个月，到期自动清理 |
| 未进食 | 记「未进食」，判定留空，不警告不催 |
| 循环方式 | 7 天一轮，DAY1 起始日可设置 |


## 9. 产品形态：桌面应用（v1.2 增补）

### 9.1 交付物
- 一个 **单文件 exe**，双击打开，不需要装 Python；放桌面或 U 盘都行
- 关闭窗口 = **缩小到托盘继续跑**（否则定时就断了）；托盘菜单：打开 / 立即提醒 / 暂停今天 / 退出
- 数据放 `%APPDATA%/三餐助手/`（config.json、standards.json、meals.db、logs），换 exe 位置不丢数据
- 首次启动走一次向导：填她的备注 → 检测微信 → 发一条测试消息 → 完成

### 9.2 五个页面

| 页面 | 内容 | 关键操作 |
|---|---|---|
| **今日** | 三张餐次卡片（时间、状态：未到/已提醒/已回复/超标/未报备）、最近记录 | 立即提醒、查看详情 |
| **记录** | 按天列出三餐，点开看原文、照片、判定、发出的回复 | 改判定、补录、删除 |
| **餐标** | 表格：类别、别名、标准份量、上限份量、超标话术；另加总量 | 增删类别、改数值，保存即生效 |
| **设置** | 三餐时间、她的备注、等待窗口、开关（自动回复/超标提醒）、开机自启 | 改完立即重排 |
| **诊断** | 微信窗口状态、读库是否正常、最近 20 条错误、测试发送 | 一键检测 |

### 9.3 交互决策
- **改时间立即生效**：保存后重算下一次触发，不用重启
- **超标提醒可关**：默认开；关掉后只记录不判
- **看懂与否都要留痕**：记录页能看出「这条是语音/没看懂/已判定」
- **一键测试发送**：发给文件传输助手，不打扰她
- **暂停今天**：临时不想打扰她时用，次日自动恢复

### 9.4 技术选型
- **Tkinter + ttk**（Python 自带）：打包后 exe 约 15MB，启动 1 秒内，不需要额外运行时
- 不用 Qt：安装包 60MB+，启动慢，对这个小工具不划算
- 托盘用 `pystray`（约 50KB），打包一并带上
- 打包用 PyInstaller `--onefile --windowed`，带图标和版本信息
- 界面做暗色/浅色两套配色，字体用微软雅黑，不用系统默认的宋体

### 9.5 状态与兜底
- 微信没开/没登录：首页顶部红条 +「去检查」，到点不发、不猜
- 读库失败：黄条提示「降级为截图识别」，功能不中断
- 托盘图标颜色反映状态：绿=正常，黄=有未报备，红=故障

## 10. 验收

连续 3 天 9 顿全自动：每顿都发出且校验通过；她的回复都读到；未识别的只记录不打扰；
无重复回复、无发错人；失败会通知你。

## 11. 技术风险（编码第一天验证）

1. 能否从 `Weixin.exe` 内存取到 message_0.db 的密钥并解密 —— 方案成立与否的关键
2. 能否稳定定位她的会话与图片路径
3. 发送后「读库确认」是否足够快（WAL 落盘延迟）

任一不成立 → 整体切截图 OCR 路线（已实测可行），其余设计不变。
